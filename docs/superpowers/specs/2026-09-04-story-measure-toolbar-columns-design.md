# Story Measure and Toolbar Columns Design

**Date:** 2026-09-04
**Status:** Approved
**Repository:** `MentallyQuill/PomegranateUI`

## Outcome

Story-stage Panels let users resize the Story transcript and composer as one centered reading measure. The left and right instrument toolbars can contain explicit columns, added and removed with compact `+` and `−` controls styled like the existing toolbar controls.

These are reusable PomegranateUI layout behaviors. They do not introduce product branding, domain-specific Widget semantics, theme-ID branches, or a new Panel template family.

## Chosen approach

Toolbar columns are explicit layout lanes. They are not inferred from toolbar width and are not generated by mutating the Panel template.

The `story-stage.v1` template retains its four semantic regions:

1. left instruments
2. stage
3. composer
4. right instruments

The left and right instrument regions each own one or more internal columns. The original outer column is permanent. New columns are appended inward, toward the Story stage. The same innermost column is always the target of removal.

This preserves stable Widget placement and gives `+` and `−` predictable meaning. Adopter-defined templates remain independent of a user's column count.

## Story reading measure

Each Story Panel stores one preferred reading measure shared by the transcript and composer. The default is 800 CSS pixels and the desktop minimum is 420 CSS pixels. The rendered measure is the preferred measure clamped to the space currently available inside the Story stage, including the existing theme-authored outer gutters.

The preferred value is not overwritten when toolbar growth or viewport contraction temporarily reduces the available space. When space returns, the Story transcript and composer return to the saved preference. If the user starts a resize while the measure is clamped, the drag begins from the rendered width so the first movement responds immediately; completing that drag deliberately replaces the older preference.

Themes may retain distinct internal prose padding, borders, materials, and optical gutters. The shared measure controls the centered outer envelope; it does not require every theme's painted transcript edge to equal its painted composer edge.

## Story resize interaction

The composer exposes a 12-pixel vertical resize zone at each outer edge on fine-pointer layouts. The shared recipe marks them with `data-story-measure-resizer="left"` and `data-story-measure-resizer="right"` and the semantic part `story.measure-resizer`. Hovering either zone exposes the browser's `col-resize` cursor. A fine grip appears only while the zone is hovered, keyboard-focused, or actively dragged, using the same separator vocabulary as existing layout resizers.

Dragging either edge changes the shared measure symmetrically around the Story stage centerline:

- Pulling an edge outward expands the transcript and composer.
- Pulling an edge inward contracts them.
- The horizontal center does not move.
- Pointer cancellation restores the measure from the start of the drag.
- Double-click restores the authored 800-pixel default.
- A click or tap without a resize gesture does not collapse, expand, or otherwise mutate the Story surface.

Each edge is a focusable vertical separator. The accessible names are `Resize Story width from left edge` and `Resize Story width from right edge`, and each value exposes the current rendered width in pixels. Arrow keys move the focused edge spatially, Home selects the minimum, and End selects the largest width currently available.

On coarse-pointer layouts where Story toolbars still render, the interactive edge target is at least 44 pixels while the painted grip remains subtle. At compact/mobile collapse, the handles disappear and the Story content uses the existing fluid-width presentation. The desktop preference remains saved.

## Toolbar column structure

Each Story Panel stores, independently for the left and right toolbar:

- its requested total width;
- a column count whose zero-based indices are stable because columns are only appended and removed at the inner edge;
- each shelf's column assignment, through which its docked Widgets inherit that assignment.

The public model represents this with an optional typed `storyLayout` value on `PanelState`. It contains `preferredMeasure` and the left and right toolbar column counts. Existing `configuration.dockWidths` remains the requested-width owner. `ShelfState` gains an optional zero-based `dockColumn`; an omitted value has legacy meaning and resolves to outer column zero.

`dockColumn` is valid only for a shelf in a Story Panel's left- or right-instruments region and must be lower than that edge's current column count. The contracts schema encodes the structural bounds; layout validates the cross-record reference against current Panel state.

The outer column is index zero and cannot be removed. Added columns receive the next index inward. Existing columns keep their indices and assignments because only the highest, innermost index may be removed.

Columns divide the rendered toolbar width evenly. Adding a column expands the toolbar to provide the new lane with the normal authored Widget width when the viewport permits. Manual toolbar resizing remains available, but the rendered width is constrained by:

- a usable minimum width for every visible column;
- the space required by the opposite toolbar;
- the minimum usable Story stage and its outer gutters;
- the current viewport.

The saved requested width is preserved when viewport constraints temporarily clamp the rendered width. If the user resizes a clamped toolbar, the gesture begins from its rendered width and the completed gesture deliberately replaces the older request.

## Column controls

An open toolbar displays adjacent square `−` and `+` buttons at its bottom inner corner. On fine-pointer layouts, each side equals the existing toolbar edge control's 30-pixel cross-axis thickness; coarse-pointer targets are 44 by 44 pixels. They inherit the material, border, radius, symbol weight, hover, focus, pressed, and disabled treatment of the existing Open/Close Toolbar control family. The symbols are optically centered.

The visible content is only `+` and `−`. Accessible names use natural language, such as `Add column to left toolbar` and `Remove column from right toolbar`.

- `+` adds one empty innermost column.
- `−` removes the innermost column.
- `−` is disabled when only the permanent outer column remains.
- `+` is disabled when another column cannot fit while preserving the minimum center stage.
- Both controls are hidden while their toolbar is closed or responsively compressed.

## Removing a populated column

Removing an empty innermost column is immediate. If the column contains Widgets, the UI opens a confirmation dialog before changing state.

The dialog:

- states that removing the column also removes its Widgets from the current Panel;
- reports the affected Widget count;
- lists every affected Widget by its current display name in a scrollable region when necessary;
- focuses `Cancel` initially;
- provides `Cancel` and `Remove column` actions;
- returns focus to the toolbar's `−` control after cancellation;
- after confirmation, returns focus to the remaining `−` control when it is enabled, or to `+` when only the permanent column remains;
- uses the application's established dialog and destructive-action styling.

Confirmation atomically removes the column, its shelves, its visible Widget instances, and their placements from the active Panel. A shelved Widget is not actively in the column; if its remembered placement references a removed shelf, that remembered placement moves to the outer column's primary shelf so the Widget remains restorable. Column removal does not unregister Widget types from the Catalog and does not affect Widgets in another Panel. The existing layout Undo operation restores the column, its width context, every removed Widget instance, tab grouping, ordering, shelf, and placement.

The confirmation records the exact Widget instance IDs shown to the user. On confirmation, the layout operation compares that set with the column's current contents. If they differ, it rejects the stale request without removing anything, refreshes the dialog, and requires a new confirmation. This prevents an unlisted Widget from being removed if the layout changes while the dialog is open.

Escape, dialog dismissal, and `Cancel` leave state unchanged.

## Commands and events

The contracts layer adds typed commands and matching events for:

- setting the preferred Story measure;
- adding the next innermost column to a Story toolbar edge;
- removing the current innermost column with the expected visible Widget-instance set;
- the resulting column-added, column-removed, and Story-measure-changed outcomes.

The existing dock-resize command remains the owner of requested toolbar width, but its validation and layout operation must support multi-column bounds instead of the current fixed one-column maximum.

Pointer movement may update live geometry, but one completed drag produces one meaningful Undo record and persisted resize. Column addition and confirmed column removal each produce one atomic revision and one Undo record.

All untrusted command and saved-layout input is parsed through `@pomegranate-ui/contracts`. Layout owns normalization and pure transitions. Core owns command routing, projection, events, and Undo. The Svelte recipe translates input gestures into public commands and renders projected state without theme-specific behavior branches.

## Persistence and recovery

The new fields are optional so existing layout-v3 snapshots continue to parse. A Story Panel without `storyLayout` receives one stable outer column on each toolbar and the 800-pixel Story-measure default. Existing `configuration.dockWidths` values seed the corresponding requested widths when `storyLayout` is absent, preserving layouts saved before this contract existed.

During hydration:

- an invalid column count returns to one outer column;
- an invalid preferred measure returns to the default;
- a shelf whose column index is missing or invalid moves to the matching toolbar's outer column without removing its Widgets;
- a requested toolbar width is preserved when valid and otherwise returns to its authored default.

Encoding remains deterministic. Panel duplication preserves the same visible layout and zero-based column assignments.

## Responsive behavior

At widths that cannot display every saved toolbar column with a usable lane width, each toolbar temporarily presents its Widgets as one combined vertical lane. This visual compression does not rewrite column identifiers or Widget assignments. Column controls are hidden in this state.

At the existing compact breakpoint, the instrument toolbars hide and the Story transcript and composer become fluid-width. Returning to a sufficiently wide viewport restores the exact saved column structure, assignments, requested toolbar widths, and preferred Story measure.

Responsive presentation never deletes a column or Widget and never opens a destructive confirmation dialog.

## Failure behavior

- Adding a column when insufficient space remains is prevented by the disabled `+` control and rejected by the layout operation if invoked programmatically.
- Removing the permanent outer column is rejected.
- Removing any column other than the current innermost column is rejected.
- A stale populated-column confirmation is rejected without partial mutation.
- Invalid resize values are rejected or normalized at the public boundary; rendered geometry never becomes negative, non-finite, or wider than the layout solver permits.
- Pointer cancellation restores pre-drag geometry and does not add an Undo entry.

Every rejected operation leaves the prior Workbench state unchanged and returns a typed error suitable for a calm user-facing status message.

## Out of scope

- Automatic column creation based only on dragged toolbar width.
- Arbitrary middle-column insertion or removal.
- Unequal widths between columns in the same toolbar.
- Moving Widgets automatically before a column is removed.
- Deleting Widget types from the Catalog.
- Applying Story-measure controls to non-Story Panel families.
- Theme-specific markup or behavior forks.
